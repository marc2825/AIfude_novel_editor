# Phase 6：原稿同期のローカル基盤

2026-10-28、C-01〜08を対象とした設計。ローカルで検証できる保存・通信契約・競合保護を実装する。本番の認証、接続先、HTTPS配備は未決定で、製品画面のネットワーク同期は有効にしない。

## データ契約

WorkspaceSnapshotはv6のまま、IndexedDBをv4からv5へ進めて同期状態storeを追加する。既存原稿は変換・削除せず、旧v1〜v5の読み込みは既存の移行処理を使う。

SyncPayload v1には作品・全章・作品メモリ・authoring profile・文体・執筆設定・最大50件の保存履歴を含める。AI同意・モデル接続設定・認証情報・UI位置・local storageVersionは含めない。利用者が本文やメモに書いた秘密情報を、アプリが完全に検出することはできない。

10MiBの上限と形式・参照ID・重複を両側で検証し、未知の形式は拒否する。章や履歴を黙って減らさず、章の順序を正規化する。開いている章の違いだけでは同期しない。

サーバーは作品単位のrevisionをCASで更新し、全章とメモを一度に保存する。章ごとの自動mergeやCRDTは実装しない。

## 送信待ちと応答

同期は初期OFF。利用者の操作で保存済み原稿から送信待ちを作る。pendingの内容はoperation IDごとに固定し、待機中の編集は通常の自動保存へ送る。ack後に次の原稿を準備する。通信復旧だけでは再送しない。

pending・ack・競合コピーはIndexedDBのstrict readwriteトランザクションでCASする。本文と履歴も同じトランザクションで読み出す。同期プロトコルはWeb Locksに依存せず、現在のエディタ保護にだけ既存のWeb Lockを使う。

ackは現在のpending IDと照合し、古い・重複・逆順の応答で新しい送信待ちを変えない。切断・認証失効・時間切れ後は同じoperation IDで再実行し、サーバーのreceiptで二重保存を防ぐ。

## 競合と削除

CASが衝突したら、送信版とサーバー版を同じトランザクションで残す。自動上書きせず、両版を確認してコピーとして作品に復元できるようにする。次の送信準備も利用者が選び、サーバーがさらに更新されていれば再度競合として保持する。

同期コピーは最大20件。上限では新しい処理を保留して失敗を示し、未確認コピーを自動削除しない。確認済みコピーの削除はsequence CASで行い、競合未解決中は削除できない。

送信待ちとコピーは移行ファイルへ書き出せる。通常の作品・全作品バックアップには同期状態を入れない。必要なコピーを作品へ復元すれば、通常のバックアップにも含められる。

ごみ箱へ移す段階では同期状態を残す。最後の作品・ごみ箱コピーを完全削除するときに、その作品のoutbox・同期コピーも同じトランザクションで消す。これをサーバー削除の指示には変換しない。

初期の受信適用はコピー復元に限る。編集中の本文の自動差替え、定期的なbackground sync、同期削除・tombstoneは未実装。

## サーバーと認証の境界

Node 24のSQLiteを使い、`BEGIN IMMEDIATE`、WAL、`synchronous FULL` でrevision・receipt・過去改訂を原子的に保存する。別connectionからのCASにも対応し、失敗時はROLLBACK。IDを検証し、SQL値はparameter bindingで渡す。

SQLiteの `user_version=1` とし、未知の版は拒否する。暫定上限はアカウントごと100作品、1,000 receipts、100MiB。古いreceiptや改訂を消して再送の安全性を失わないよう、上限で新規保存を止める。実運用の保持期間は未決定。参考：[Node 24 SQLite](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html)。固定のNode 24.21.0でも検査する。

principalは認証済みアダプターから渡し、本文にaccount / ownerを指定させない。作品・receiptはアカウントごとに分け、未認証・別アカウント・同じoperation IDで異なる内容・不正なbase revisionを拒否する。公開APIは設けない。

HTTP transportは同一originとHTTPSを要求し、テスト環境だけループバックHTTPを許可する。認証はcookieや認証アダプターの責務とし、送信データには含めない。Origin・header・Content-Type・テスト用sessionを検証し、リダイレクト禁止、no-store、応答上限、時間制限、遅延応答の照合を適用する。

E2EE・ゼロ知識は未実装で、サーバー管理者は原稿を読める。公開運用には保存時暗号化、鍵管理、アカウント回復・端末失効、cookie・CSRF、回数と容量制限、HTTPS終端を決めた上で、別途セキュリティ確認が必要。
