# AIFUDE — 日本語小説特化・スマホ対応・PC同期 要件定義書

- 文書ID: ANE-JM-REQ-001
- 版: 1.0（2026-10-26）
- 対象: AIFUDE の日本語・モバイル拡張
- 実装元: 作品メモリと局所編集を備えた既存版（2026-10-26の策定時点）。旧非公開リポジトリの識別子とコミット参照は配布文書から除外する。
- 原則: 原稿は著者が管理し、AIの編集は必ず明示的な採用操作の後に限る。
- ステータス: 実装用要件案。機能の達成や実機検証を主張する文書ではない。

## 0. 要約と意思決定

Sudowriteと同じ「文章の続きをAIが書く」一般用途を競争軸にしない。差別化の中心を次の**連続したユーザー体験**に置く。

1. 日本語の小説を書きやすい（IME、句読点、台詞、縦書き確認、ルビ・傍点）。
2. 原稿を診断する（反復、語尾、リズム、人物の口調、設定・文脈整合）。
3. 問題と根拠を明示し、修正可否・保持ルールを著者が制御する。
4. 複数モデルの推敲候補を比較し、必要な差分だけ安全に採用する。
5. PCとスマホで同じ作品を安全に続け、オフラインから復帰しても原稿を失わない。

**採用するアーキテクチャ**: Next.js/React/TipTapを維持し、まずレスポンシブWeb UI、次にPWAとローカルオフライン、最後に認証・TLS・衝突保護付きの任意同期を実装する。iOS/Androidネイティブアプリは本計画の必須要件としない。クラウドへの一般公開・有料SaaS化は対象外とする。

## 1. 根拠と現状

- 以下は策定時点の既存機能と制約の記録。現在の実装範囲・保存形式・公開前の残件はREADMEと `docs/PUBLISHING.md` を参照する。
- 既存: 複数作品・章、作品メモリ（設定・背景・登場人物の手動入力）、検索置換、履歴・ごみ箱、選択範囲のRewrite/Transform/Expand/Condense、辞書、Infill/Continue/Context Insert、複数AI比較、Diff/明示Accept/単一Undo、ローカルIndexedDB、バックアップ。既存実装・テストを優先して再利用する。
- **現時点の制約**: `127.0.0.1` に限定されたローカルサーバー、単一ブラウザー保存領域、スマホ接続・端末間同期なし。ProseMirrorの永続本文schemaは原則 `doc/paragraph/text` のみ、workspace schema v4。AI品質・実LLM・実端末IME検証は未完了。
- 原則: 既存のREADMEと `AGENTS.md`、`docs/REQUIREMENTS.md`、`docs/ARCHITECTURE.md`、`docs/SECURITY.md`、`docs/TESTING.md`を正本として差分設計を追加する。未確認の状態を「実装済み」と断言しない。

### 1.2 Sudowriteを参考にする範囲
| Sudowriteの機能 | 判断 | 本製品への適用 |
|---|---|---|

| Feedback | 高優先で導入 | 日本語の規則検出＋AIコメント。行位置・根拠・解決操作 |
| Story Bible/Chapter Continuity | 高優先で導入 | 構造化人物・世界観・章要約・時系列。明示選択した資料のみ参照 |
| Match My Style | 高優先で導入 | 著者の文体特徴を可視化し、承認後に推敲へ反映 |

## 2. スコープ・非目標

### 2.1 対象ユーザー
日本語でWeb小説、ライトノベル、創作小説を書き、文章表現を自分で決めたい個人執筆者。PCで長文、スマホで短時間の続き執筆や推敲を行う。

### 2.2 対象（P0/P1）
- P0: スマホ・タブレットの安全な基本執筆、IME・タッチ範囲選択、画面分割に依存しない推敲UI。
- P0: 反復・語尾などの日本語診断、人物口調ルール、明示Accept、差分/部分採用、人物情報の構造化。
- P0: 既存データ保護と手戻りできるmigration、確実なバックアップ、改変リスク通知。
- P1: AI Feedback/Describe/Match My Style/章間連続性、ルビ・傍点・縦書きプレビュー、投稿サイト出力。
- P1: インストール可能なPWA、オフライン執筆、**任意の**PC・スマホ間同期（認証、HTTPS、非破壊競合処理）。

### 2.3 対象外（当面）
- チャットのみで小説全文を自動生成・自動投稿するフロー。
- AIが確認なしに原文・作品メモリを書き換える機能、黙示的な生成ループ。
- 一般向け認証付きSaaSホスティング、課金、共同リアルタイム編集、SNS機能。
- オンラインサービスの規約を回避した自動投稿、SudowriteのUIや著作物の複製。
- ローカルLLMがモバイル端末上で必ず推論できるという保証。
- 初回からのネイティブiOS/Androidアプリ配布、音声機能・プラグイン市場の構築。

## 3. UX・機能要件（識別子はテストと1対1対応）

### M: スマホUI/入力（P0）
| ID | 要件 | 受け入れ条件 |
|---|---|---|
| M-01 | レスポンシブ編集レイアウト | 320/375/390/430/768/1024px幅で横スクロールや主要操作欠落がない。PCレイアウトの劣化がない |
| M-02 | 編集中心のモバイルUI | 作品/章切替、本文、保存状態を最上位。補助パネルはドロワー/ボトムシート。AI生成ボタンと採用ボタンは明瞭 |
| M-03 | タッチ選択からAI提案 | テキスト選択→提案→入力→結果比較→採用までマウス・右クリック・キーボードショートカット不要で実行可能 |
| M-04 | ソフトウェアキーボード | iOS Safari / Android ChromeのIME変換中に意図しない改行・selection喪失・フォーカス喪失・誤Acceptが起きない。viewport縮小とsafe areaに対応 |
| M-05 | 候補比較 | 画面幅により横並び・カード切替を変更。原文・モデル名・差分・採用可否・staleが確認できる |
| M-06 | アクセシビリティ | タッチターゲット目標44×44 CSS px以上、ラベル・focus管理・スクリーンリーダーで基本操作可能、reduced-motion対応 |
| M-07 | 継続編集 | バックグラウンド復帰や画面回転で本文と未保存入力を保護。未保存時に成功状態を偽装しない |

### J: 日本語推敲・作者の意図保護（P0）
| ID | 要件 | 受け入れ条件 |
|---|---|---|
| J-01 | 非生成型の日本語診断 | 語の過度な反復、文末表現の連続、表記ゆれ候補、重複接続表現、句読点/括弧不整合、文長・会話文比率を**検出可能な範囲で**提示。規則と閾値を記載 |
| J-02 | 誤検出への配慮 | 直接「誤り」と断定せず「確認候補」とする。台詞/固有名詞/意図した反復は無視登録可能。本文自動変更なし |
| J-03 | 診断から推敲 | 診断→対象の安全なselection snapshot→既存AI編集へ接続。AIは送信前の明示操作のみ。設定・保持条件・モデルを可視化 |
| J-04 | 口調プロファイル | 登場人物ごとの一人称・二人称・呼称・敬体/常体・語尾・例文・禁止事項。ルール違反は根拠と対象箇所を提示 |
| J-05 | 作者文体プロファイル | 文長分布・句読点・漢字/ひらがな比率等の**観測可能な特徴**と例を表示。AIによる説明は推定であると区別。適用前に承認 |
| J-06 | 保持制約の選択 | 固有名詞、出来事、時系列、POV、台詞意味、人物呼称など。意味保持はLLMだけで保証せず、決定的な変更検出と警告を併用 |
| J-07 | 日本語フィードバック | 章全体/選択範囲にコメント。対象位置、問題、根拠、改善案。内容変更後はアンカーを再検証/失効。AIコメントは自動採用しない |
| J-08 | プロンプトとベンチマーク | 日本語文体・口調・設定保持・編集時間・選択正確性を比較。AIモデルとエディタUXの寄与を分けて記録 |

### A: AI編集と候補操作（P0/P1）

| A-02 | 既存複数AI比較の改善 | 提供元・モデル・費用/利用枠の区分・送信範囲を表示。同一条件比較。一方の失敗で他の成功を破棄しない |
| A-03 | 描写案（Describe） | 五感/比喩/内面を切替可能。提案を見てから挿入・コピー。追加事実の創作可否を明示 |
| A-04 | 文体変換/Quick Edit | inlineにプレビュー、差分、再指示、採用・却下。既存の外部候補UIと同じ安全なAccept経路を使用 |
| A-05 | Chapter Continuity | 章要約・人物状態・時系列・世界観を明示選択して参照。章外の内容を黙って送信しない。関連元の章を示す |
| A-06 | Guided Write | 次に起こす内容と長さを指定し、少なくとも2案比較可能。現在のContinue/Context Insertを再利用 |

### S: 構造化メモリと長編整合（P0/P1）
| ID | 要件 | 受け入れ条件 |
|---|---|---|
| S-01 | 作品メモリ構造化 | Character/WorldRule/Relationship/TimelineEvent/ChapterSummaryの識別子・出典・更新日時を管理。現行3欄メモは保持 |
| S-02 | 明示参照 | AIに送信する資料を生成ごとに選択、初期OFF、送信内容/文字数・トークン予算を確認可能 |

| S-04 | 整合性チェック | 章横断の人物呼称、重要固有名詞、時系列、現在地などを検査可能な範囲で警告。出典箇所と確信度を提示。誤検出可 |

| ID | 要件 | 受け入れ条件 |
|---|---|---|
| T-01 | ルビ・傍点の表現 | 原稿内部では装飾を構造化/可逆表現で保持。単なる表示だけのルビと実本文の関係を維持 |
| T-02 | 縦書きプレビュー | 読書・校正用の縦書き表示。初期は横書き編集を正本とし、選択位置が壊れる場合は縦書きを閲覧専用にする |
| T-03 | サイト別エクスポート | カクヨム・小説家になろう向けルビ/傍点・章区切り変換、プレーンtxt、JSON全文バックアップ |
| T-04 | 可逆性と検証 | 変換前後の本文とルビ対応のround-tripを試験。サイト仕様の差/制限/エスケープを文書化 |

**構造上の注意**: 現在のPM schemaは `doc/paragraph/text`。ルビ対応をプレーンテキストへの危険な一括置換で済ませない。先に ADR を作り、マーク/インラインノード/sidecar annotationの長短・PM位置・Diff・JSON migrationを検討してから、後方互換を担保して導入する。

### P: PWA・オフライン（P1）
| ID | 要件 | 受け入れ条件 |
|---|---|---|
| P-01 | PWA installability | manifest, icons, standalone viewport, iOSのホーム画面追加ガイド。インストール可否は実端末で別途判定 |
| P-02 | オフライン本文 | 一度正常起動し必要な静的資産を保存した端末で、通信切断後にも現在保存済みの原稿の閲覧・編集・ローカル保存が可能 |
| P-03 | AIのオフライン挙動 | モデルが接続不能なら生成ボタンを無効化/理由表示。既存本文の編集・保存は継続し、自動で別providerへ送信しない |
| P-04 | Cache/情報保護 | `POST /api/ai/*`、認証・資格情報・本文/AIレスポンスをService Worker/CacheStorageにキャッシュしない。旧版キャッシュ破棄の安全策がある |
| P-05 | 更新失敗復旧 | SW更新・タブ再起動・オフライン⇄オンライン遷移で原稿を喪失しない。旧/新schema混在時は安全停止・バックアップ促進 |

### C: PC・スマホ同期（P1だが独立のセキュリティgate）
| ID | 要件 | 受け入れ条件 |
|---|---|---|
| C-01 | opt-in同期 | 同期は初期OFF。ローカルのみで使用可能。接続設定は利用者の明示操作で開始/解除できる |
| C-02 | TLS/認証 | インターネットから触れる同期エンドポイントはHTTPS+強い認証+認可が必須。プレーンHTTP/LAN公開・匿名編集を行わない |
| C-03 | 差分・改訂管理 | 作品/章レベルのserver revision/ETag・CAS。競合を黙って上書きせず両方の本文を復元可能な形で保持 |
| C-04 | 端末間の同期 | 端末Aの編集が端末Bへ反映され、オフライン中のBの編集も復帰後に送信できる。衝突時に安全な選択UI |
| C-05 | local-first | ネットワーク障害/認証失効時もローカル編集継続。同期成功とローカル保存済みを別状態として表示 |
| C-06 | バックアップ/移行 | 既存v1-v4バックアップを読み取り可能。全文バックアップから新端末に復元できる。同期削除とローカル削除を混同しない |
| C-07 | プライバシー | 送信先、保存先、保護方式、暗号化範囲、復元方法を表示。監査済みでなければE2EEやゼロ知識を主張しない |
| C-08 | multi-device検証 | 分離した2 browser profile + simulated offline + 同時編集 + 再認証 + rollback + 削除・復元の統合試験が通る |

**実装上の安全方針**:
- 現在のlocalhost専用AI APIを、認証なしに LAN / 0.0.0.0 へ公開してはならない。
- 「スマホから使うために `APP_ORIGIN` を0.0.0.0にする」等の安易な対応は禁止。
- 同期サーバーは既存AI APIと境界を分離。適切な認証・セッション・CSRF/Origin防御・レート制限・容量制限・リビジョン・復旧策を実装する。
- 同期基盤の種類（自己ホストか外部サービスか、DB、鍵管理）は**セキュリティADR**でトレードオフを比較してから確定する。資格情報・公開URLを勝手に作成しない。インフラ用クレデンシャルがない環境でも、ローカルに閉じたテスト用sync fixtureで機能検証する。
- E2EEを採用するなら端末鍵の配布・紛失復旧・鍵ローテーション・暗号化メタデータまで設計。未実装なら「サーバーからは見えない」と書かない。

## 4. 横断的な非機能要件

**D（原稿保全）**: いずれのAI・オフライン・migration・同期処理も、原稿の保存に失敗した状態を「保存済み」と表示しない。旧原稿・バックアップを破棄せずに処理。競合は自動上書きしない。単一Undo、範囲外不変、stale拒否を保持。

**I（日本語入力）**: 実OS日本語IME、Android Gboard、iOS日本語キーボードのcomposition・変換確定・改行を区別。iOS Safariのselection/touch/popupとキーボード表示変化を実機で確認。

**R（応答性）**: 既存10万文字級PCパフォーマンス試験を維持。モバイル2万文字程度で入力やスクロールの顕著な遅延がないことを実測し結果記録。診断はdebounce/worker等で執筆をブロックしない。実機数値未測定のまま定量的達成を主張しない。

**Q（生成品質）**: 固有名詞・呼称・意味保持をLLMに強制したと断言しない。人手レビュー前提。統計検出とモデル推論を区別し、確実性の水準を表示。

**S（セキュリティ）**: 認証token・API keyはクライアントバンドル・バックアップ・ログへ出さない。本文の無断送信禁止。比較AIで各送信先と利用枠を示す。XSS/CSP/Origin/CSRF/SSRF/Rate-limitは既存水準を下げない。

**A（アクセシビリティ）**: PC keyboard、タッチ操作、画面読み上げ、視認性/高コントラストを考慮。ダイアログでfocusが失われた場合の復帰先を定義。

## 6. テスト計画（必須）

### 6.1 自動テスト
- unit: 日本語検出、表記揺れの偽陽性、話者口調ルール、Unicode、ルビ記法、選択/文節抽出、migration、sync conflict。
- property test: 旧データ→新データ→backup→importの無損失、AI部分採用時の範囲外不変/Undo/Redo、Unicode surrogate/絵文字/改行。
- component: 320〜430px viewport、タッチメニュー、ボトムシート、フォーカス復帰、未保存稿、候補を切り替えたときのstale。
- E2E: desktop baseline + Playwright Android系mobile emulation + WebKit可能時の検証 + PWAオフライン + 2プロファイル同期競合・回復。
- security: オフラインキャッシュに本文や秘密が入らないこと、匿名APIアクセス不可、CSRF、同期改訂race、無制限送信・高額API課金を防ぐ。
- fixture: 個人の実原稿ではなく、合成日本語小説の会話/地の文/台詞/名前/ルビ/改行を使用する。

### 6.2 人手・実機gate（試験していなければNOT RUN）
- Windows Microsoft IME＋Chrome、macOS日本語IME＋Safari/Chrome。
- iOS Safari（ホーム画面版含む）＋日本語キーボード、Android Chrome＋日本語キーボード。
- タッチ範囲選択、キーボード出現・閉鎖、スクロール、バックグラウンド復帰、回転、低メモリ・通信断。
- スクリーンリーダー（VoiceOver/NVDA等）、片手操作の確認。
- 実際のLLM接続・日本語文章品質、作品設定/人物口調の維持。
- TLS/認証/復旧の実環境テスト完了前に、PC同期を公開対応と宣言しない。

### 6.3 ベンチマーク
- 目標データ: 30〜50箇所以上の日本語文章（台詞、地の文、文体差、設定矛盾、既存書き直し例）。機密原稿は使わない。
- ブラインド評価: 日本語自然さ、意味・人物・視点の保持、編集意図、採用率。複数人なら評価者間差も記録。
- 体験評価: 同一タスクの操作数、所要時間、間違って原稿を変更した回数、端末別失敗率。
- 比較対象: Sudowrite等と、可能な範囲で同一本文/同一プロンプト。AIモデル差とUI差を区別し、条件を明記。

## 7. Definition of Done / リリース基準

各Phaseで最低限: `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build`, 該当Playwright E2Eを実行し、実行結果/環境/未実施/証拠を `docs/` に記録。全E2Eは実行可能なら実施。失敗や未実施をPASSと表現しない。既存機能の回帰があればPhase完成としない。

最終版の公開GOは、スマホ実機で編集・復旧確認、同期の認証/衝突/復旧、既存PC編集の回帰、日本語ルビの入出力・旧バックアップ移行、最低限のAI文章品質の評価が揃った場合だけ。作業途中は段階別にGO/NO-GOと記す。実行不能な実機試験が残る限り最終Releaseは `NOT YET VERIFIED` とする。

## 8. バージョニングと既存実装の保護

- `WORKSPACE_SCHEMA_VERSION = 4` の既存データを失わない。新フィールド追加時は明示的なv5以降のschema migration、旧v1〜v4のimport/migration、future version fail-closed。
- migrationの前後で本文/章数/ID/改行/メモ/モデル設定/履歴の扱いを確定し、schema拡張を関係ないPhaseで行わない。
- 既存のTipTap正本、Web Locks、安全なAccept transaction、外部送信明示同意、API初期OFF、ローカル保存/バックアップを壊さない。
- 同期は保存方式の置き換えではなくlocal-first追加層とする。同期接続の有無を原因とする原稿消失を許さない。
- 現行の日本語本文の生テキスト、台詞括弧、改行、ルビに似たリテラル記号を勝手に正規化しない。

## 9. 優先順位と延期条件

- P0のM/J/A主要フローを**実際に快適に使えること**を先に証明する。機能を増やし過ぎてUIを複雑にしない。
- 日本語形態素解析器の導入は辞書サイズ・初回ロード・オフライン・ライセンス・誤検出率を調べてADR判断。まず再現性のある軽量規則から始める。
- ルビの構造と同期エンジンの実装はデータ損失リスクが高いため、互換/rollback設計・テスト前には着手しない。
- Plugin marketplace/音声変換/章全文自動生成は初期リリースのブロッカーにしない。
