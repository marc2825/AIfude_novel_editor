# レスポンシブ画面・PWA・同期の方針

2026-10-26に、最初の段階としてレスポンシブ画面を採用した。以下は段階設計の記録であり、現在の実装範囲は [ロードマップ](IMPLEMENTATION_PLAN.md) を参照する。本番インフラと暗号方式は未決定。

## 画面

Next.js / React / TipTapを維持する。PCでは中央本文と右パネル、狭い画面では同じエディタとフォームを再配置する。パネルの開閉で入力を捨てず、AI画面は本文を編集できる非モーダル形式とする。

タップも既存の選択取得・コントローラー・同期採用へつなぐ。標準の長押し選択を妨げず、IME変換中はAI操作をしない。blurやリサイズで古い選択を設定し直さない。

高さはVisualViewportのheight / offsetに追従し、使えない場合はdvhを使う。safe areaを確保してズームを禁止しない。狭い画面の入力欄は16px以上、主要ボタンは44pxを目標とする。回転・スクロールでエディタを作り直さない。

「本文へ」と「AI画面に戻る」で指示・候補を保持して行き来できる。本文や選択が変われば候補は期限切れになり、閉じる操作ではセッションを捨てる。

## 実装の段階

1. Phase 1は表示と操作。ループバック・APP_ORIGIN・認証・保存形式を変えず、スマホとの接続のためにLANへ公開しない。
2. Phase 5は静的な画面のキャッシュ。原稿はIndexedDBへ残し、API・認証・原稿・バックアップ・接続設定はCacheStorageへ入れない。ビルドで秘密情報の混入を検査し、未保存入力のある画面を強制更新しない。新旧形式が混ざる場合は旧書き込みを止め、バックアップを案内する。
3. Phase 6はローカル保存に同期基盤を追加する。初期OFFとし、未接続・失効・通信失敗でも編集保存を続ける。ローカル保存と同期完了を分け、既存AI APIを公開同期APIへ転用しない。

背景化では保存を試みるが、OS終了や保存領域の削除に対する完了保証はしない。

## 同期方式の候補

| 方式 | 利点 | 必要な確認 |
|---|---|---|
| 自己ホストのHTTPS・認証付き同期 | 保存先を管理し、CASに合うデータ設計を使える | 証明書・更新・認証・バックアップ・端末からの到達性 |
| 管理サービスの認証とDB | TLS・認証・運用の一部を任せられる | 契約・費用・データ所在地・権限・サービスへの依存 |
| バックアップの手動移送 | 既存のコピー復元を使え、インフラ不要 | 自動同期ではない。重複と併存コピーを利用者が管理する |

当初案は作品・章revisionとETagのCAS、operation IDによる再送の重複防止。時刻で勝者を決めず、競合では両版と共通祖先のメタデータを残す。解決は明示保存とし、削除のtombstone・保持期限・復元も別に設計する。Phase 6で採用した範囲は [同期基盤の設計](ADR_LOCAL_SYNC.md) に記載する。

## セキュリティと検査

本番同期にはHTTPS、認証と作品ごとの認可、セッション失効、CSRF・Origin・Host、回数・容量制限、SSRF・リダイレクト対策、ログの秘匿が必要。同期認証を作品バックアップへ入れず、プロバイダーのキーもブラウザーへ渡さない。

E2EEは未採用。TLSやサーバー保存時暗号化とは分け、採用するなら端末鍵の配布、紛失復旧、鍵更新、メタデータの漏えい、バックアップ鍵まで設計する。未監査でゼロ知識とは表示しない。

移行は旧データを残して検証してから書き込む。2つのブラウザープロファイルとテスト用認証で、同時編集・CAS競合・再送・失効・削除復元・容量・ロールバックを試す。ネイティブアプリ、無認証LAN、自動last-write-winsは採用しない。
